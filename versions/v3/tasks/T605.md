# T605: Retry status line (`retrying (n/10) in <wait>`)

Phase 6 · Model: sonnet: wires an existing provider event through the agent to the status line; no
new security logic · Depends-on: T302, T402 · Covers: R37 (status line while waiting), A10 (added by
the supervisor: T302 only emits `provider.EventRetry`; nothing consumed it)

## Brief
T302 made `internal/provider/client.go` emit `provider.EventRetry` (field `Event.Retry` with
`Attempt` 2..10, `Max`, `Wait`, `Reason`) before each retry wait. The agent loop currently ignores
unknown provider event kinds and the TUI shows nothing, so the user sees a silent hang. Fix that:

- `internal/agent`: forward each `provider.EventRetry` of a turn's stream as a new additive agent
  event kind `EvRetry` (events.go) carrying the attempt, the max and the wait (a small struct or
  fields on `Event`; `Event.Text` also holds the final display string
  `retrying (<n>/<max>) in <wait>` with the wait rendered as `1s`, `2s`, … `1m0s` →
  use `time.Duration.String()` rounded to seconds, `60s` is shown as `1m0s`: that is fine). It is
  not part of the conversation history and not a final event; the turn continues normally.
  Subagent streams forward it too, tagged with the subagent's id, or are ignored for subagents —
  your choice, state it in a code comment. Never put the provider `Reason` text into the display
  string (it may carry host details; the status line shows only attempt and wait).
- `internal/tui`: while a retry wait is pending, the status line (see `status.go`) shows
  `retrying (n/10) in <wait>` in the dim style used for the other status hints, on the tab whose
  session sent it. It disappears on the next streamed delta / tool call / done / error / cancel of
  that turn (clear it where the turn's other live state is reset, see `turn.go`). No other view
  change; nothing is appended to the conversation; the tab bar, overlays and queue are unchanged.
- Tests must not sleep: the provider's wait is the unexported `retryWait` in `client.go`. For the
  agent-level test add a small exported seam in `internal/provider` (for example
  `func (c *Client) SetRetryWait(fn func(ctx context.Context, d time.Duration) error)` or a
  functional option) that tests use to stub the wait; keep the default behaviour byte-identical
  and do not use any of the identifiers `scriptre`, `scriptfail`, `failfirst`, `resets(` in
  `client.go` or `transport.go`. `transport.go` stays untouched. Use the fake provider's scripted
  failure modes (`providertest.NewWithFailures`, T301).

Tests (names exact):
- `internal/agent/retry_event_test.go` — `TestRetryEventForwarded`: one scripted 503 then a
  streamed answer, wait stubbed through the seam → the session's events contain exactly one
  `EvRetry` with attempt 2, max 10, wait 1s, before the final text; the history holds no retry
  text; the turn ends normally. `TestRetryEventNotInHistory` (negative): history contains neither
  `retrying` nor the provider's reason text.
- `internal/tui/retry_status_test.go` — `TestRetryStatusShown`: feed the model an agent
  `EvRetry` event (build the `EventMsg` as the other tui tests do, with the session of the current
  tab) → the stripped `View()` contains `retrying (2/10) in 1s`; `TestRetryStatusClearedOnDelta`
  (negative): a following text delta event removes it; `TestRetryStatusPerTab` (negative): the
  event of a background tab's session does not show the line in the current tab's view.
