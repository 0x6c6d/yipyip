# T601: Settings write path in internal/config

Phase 6 · Model: opus: a new public write path of the user's real config file (Consequential
A11; secrets must never leak: `{env:NAME}` stays literal and no resolved value is ever written —
ReOpen + R16/R13-adjacent severity) · Depends-on: T000 · Covers: R40 (config side), A11,
R16 (secrets)

## Brief
Add the settings-write path to `internal/config`. Files: `internal/config/settings.go` (new),
tests in `internal/config/settings_test.go`. The **load/merge path stays untouched** (`Load`,
`Merge`, the `{env:NAME}` resolution are not modified).

Exported surface:
```go
// SaveSettings writes default model/effort/mode into the user config file at
// path (usually GlobalPath(home)). It returns the write error, or nil. It
// never writes any other key's resolved value and never writes a resolved
// {env:NAME} secret: those tokens stay literal.
func SaveSettings(path string, model, effort, mode string) error
```
Behaviour (A11, kept exactly):
- Reads the existing file (if any) into `map[string]any` via plain `encoding/json` (unknown keys
  survive by construction); a missing file is fine (create a fresh one with only the three keys).
  An existing but **invalid** JSON file → error `could not save settings: <err>` (no overwrite
  ever happens on a parse error — the user's file must never be destroyed).
- Sets exactly the three keys `model`, `effort`, `mode` (top-level; if the current file nests
  them differently, only top-level is written — the TUI decides what passes in, this function
  does not traverse).
- Writes atomically to the user config path: temp file in the same directory (`os.CreateTemp`,
  mode 0600), full write, `Sync`, `Close`, then `os.Rename` over the original. No temp leftovers
  on error either (remove on failure). Never a partial file.
- A resolved secret value is never reachable here: `SaveSettings` takes three strings, not a
  `*Config`; it is a pure JSON file writer. (`{env:NAME}`-tokens that already sit in the file for
  other keys are preserved verbatim because the file is read as raw JSON, not resolved — that is
  the byte-for-byte preservation the acceptance criterion demands for api_key etc.)

Tests in `internal/config/settings_test.go` (names exact; use a temp `HOME`/temp path — never
the real `~/.config`):
- `TestSaveSettingsThreeKeysAtomic`: file exists with unrelated keys → after the call it parses,
  the three keys are set to the new values, every unrelated key/unknown key is unchanged, no
  temp file leftover in the directory (only the real file, `os.CreateTemp` cleanup verified),
  mode ≤ 0644/0600 (whatever you actually set — assert the doc'd value).
- `TestSaveSettingsMissingFileCreates`: no file → a new one with exactly the three keys.
- `TestSaveSettingsInvalidJSONFileNotOverwritten` (negative): `not json` on disk → error, and
  the file's bytes are unchanged (the parse error prevents the rename; byte-identity asserted).
- `TestSaveSettingsPreservesEnvTokenLiteral` (negative, the secret-critical one): a file with
  `"api_key": "{env:SECRET_VAR}"` and an unrelated `"custom": true`; call SaveSettings; the
  written bytes contain `{env:SECRET_VAR}` literally (never a resolved value, never
  `SECRET123`-style material) and `"custom": true` byte-preserved.
- `TestSaveSettingsNoResolvedSecretWritten` (negative): with a Redactor configured for value
  `SECRET123` (mimic the existing redactor tests' setup), save a settings file carrying a
  `SECRET123`-they-should-never-see value nowhere: assert the resulting file has no `SECRET123`
  anywhere and no `[redacted]` anywhere.
- `TestSaveSettingsIdempotent`: two calls with the same values → the file content is identical
  after both (no growing/mangling), and the key order is stable enough to compare (compare
  parsed maps, not raw bytes, for this one if key order churns).
