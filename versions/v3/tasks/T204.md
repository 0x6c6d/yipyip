# T204: e2e Session round-trip fidelity test

Phase 2 · Model: sonnet: e2e test against the fake provider, following the existing `./e2e`
pattern; no new security logic (the privacy negatives re-check already-built code) · Depends-on:
T101, T103, T201, T202 · Covers: R34, R31 (full flag path e2e), R33 (secret + start-dir scoping),
R16, R29 (file location), R30 (exit saves)

## Brief
New file `e2e/session_test.go` (package `e2e`; follow the existing e2e helpers' program-drive
pattern — look at `e2e/undo_test.go` / `e2e/compact_test.go` for how a scripted fake-provider run
is set up in a temp dir with a temp `HOME`; the phase-1 Store and the phase-2 resume path are
already built, so the e2e exercises the whole flow: run → save → exit → restart with `--resume <id>`
→ continue).

Two consecutive program runs against `providertest` in the same temp dir (start dir of run 1 and
run 2 identical; the fake provider records every request body and header):

- **Run 1**: scripted provider turn 1 = one tool call (a harmless `bash`-free tool, or whatever
  the existing e2e already uses for a scripted tool call — reuse it; do not introduce a new tool)
  with a tool result containing the string `SECRET123`, plus one final assistant message. Then
  exit through the real quit path (the `/exit` wiring from T103).
- **Restart with `yip --resume <id>`** (drive the real `cmd/yip` flag path or the
  `Options.ResumeData` seam T201 defined — prefer whatever the other e2e tests already use for
  program-level drives). The provider's scripted turn 2 = one plain assistant reply; from the
  test, submit one user message `turn two` to trigger it.
- **Assertions** (R34, the core of the task):
  - Recorded request 2's `messages` JSON-equal recorded request 1's `messages` array **plus
    exactly one appended user message** `turn two` (diff in the test: unmarshal both into a
    `[]map[string]any` and compare element-wise for len(1)-1 == len(0); identical otherwise).
  - Same `model` and same `reasoning_effort` in both requests, and equal to what the config
    pinned for the run.
  - The session file lives under `<startdir>/.yipyip/sessions/<id>.json` with `<id>` 12 lowercase
    hex chars; `version` is `1`; `startdir` is this temp dir.
  - The counters reported/kept after resume equal run 1's end counters (in/out/total continue, not
    reset), asserted through the session file's token fields or the run-2 status (whichever the
    e2e helpers expose).
  - `input history` continues: recall `Up` after resume finds run 1's last user message.
- **Negatives** (R33/R16):
  - The file's raw bytes contain `SECRET123` (tool results stored un-redacted, R33), but never
    contain any api-key material: with a config whose `api_key` is `{env:YIPIPI_SECRET}` /
    value `SECRET123` style (mimic the existing e2e Secret test's setup), the file holds **no**
    api key field and no `[redacted]` placeholder for it (grep the file for `"api_key"`,
    `Authorization`, and the `Bearer` prefix — all absent).
  - A second `Store` rooted at a different temp start dir lists no sessions (R33's per-dir
    scoping, asserted directly on `List()`).
- Keep everything offline (fake provider only, temp dirs, temp `HOME`); never a real host.

Tests (names exact, in `e2e/session_test.go`):
- `TestSessionRoundTripRequests`: the two-run flow above with the message-diff + model/effort +
  counters + history assertions.
- `TestSessionFileLayout` (negative side covered too): file exists at the R29 path, `version` 1,
  12-hex id, `startdir` the temp dir.
- `TestSessionNoSecretLeak` (negative): file contains `SECRET123` (expected: tool result) but no
  api-key field/`Authorization`/`Bearer`, and no `[redacted]`.
- `TestSessionPerDirectory` (negative): a Store at a sibling temp dir `List()`s zero sessions.
