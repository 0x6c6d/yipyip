# T301: Providertest pre-first-byte failure hooks

Phase 3 · Model: sonnet: extends the shared fake provider with new scripted failure modes (no
security logic, no transport change) · Depends-on: T000 · Covers: R37 (testability), R12 (changed),
R18 (offline fake only)

## Brief
Extend `internal/provider/providertest` (the shared `httptest` fake provider; follow its existing
scripting pattern — responses/scenarios are declared in the test, replayed in order) so a test can
script a failure **before the first SSE byte**:
- **connection reset**: the server closes the TCP connection (or `Hijack` then `Conn.Close())
  before writing anything) for the first N requests, then streams normally;
- **HTTP 429**: respond `429 Too Many Requests` (empty or tiny body, with `Retry-After` optional)
  for the first N requests, then stream;
- **HTTP 5xx**: respond `503 Service Unavailable` for the first N requests, then stream.

The existing per-request recording (count and bodies of received requests) must keep working so the
retry tests can assert "exactly 10 attempts, same body each time". Add the three modes without
changing any existing scenario's behaviour (old tests keep passing; do not edit them beyond what a
strictly additive scripting change requires — prefer zero edits: new modes are new option fields).

**Tests** in `internal/provider/providertest/` (names exact; package-local, using the client from
`internal/provider`):
- `TestFakeConnectionResetScripted`: fail 9× then stream; the client sees the streaming answer.
- `TestFake429Scripted` and `TestFake503Scripted`: same shape.
- `TestFakeRecordsEachAttempt`: after 2 failures + 1 success the recorder holds 3 requests with
  identical bodies (this is the assertion shape phase 3's e2e Retry reuses).
This task implements only the fake; it does **not** add the retry loop. With `go test ./internal/provider`
as-is, the 9-failure scenarios legitimately end in a client error — write these tests against
whatever the current (v2) client does: assert on the recorded request count and bodies, and that
the error/redacted-error event eventually arrives (current behaviour), NOT on success. If the
current client cannot survive a reset mid-dial at test time, drive the scenarios through the fake's
own handler-set API directly instead. Keep everything offline; never a real host.
