# T602: Settings persistence trigger in the TUI

Phase 6 · Model: opus: triggers the new public write path (Consequential A11 — every
model/effort/mode change, incl. the resumed values, must persist; a wrong write clobbers the
user's real config: destructive potential) · Depends-on: T601, T202, T402 · Covers: R40 (TUI
side + trigger), A11, R16 (secrets never written), R15 (status unchanged)

## Brief
Wire the TUI so every model/effort/mode change writes the user config via T601's
`config.SaveSettings`. Files: `internal/tui/settings.go` (new, the seam + trigger), edits in
`internal/tui/model.go` (`Options`/`New` wiring) plus the call sites of the three setters (the
`/model` picker's `setModel` path in `picker.go`, the `/effort` handler, the `/mode` handler in
`commands.go`, and T202's resume `RestoreModelEffortMode` path). Tests in
`internal/tui/settings_test.go`. Construct the path (usually `config.GlobalPath(home)`) once in
`Options` (new field `SettingsPath string`; empty = disabled — tests that don't care set "" so
nothing is written).

**Trigger rule (A11, exact)**: call `SaveSettings` on every successful change of any of:
- model (`/model <id>` or a picker `Enter`),
- effort (`/effort low|medium|high`),
- mode (`/mode auto|manual`),
- restored values (T202's resume path: once, after the restore, with the file's three values).
Not triggered by: `/sessions` list/rm, tab switches (they change no global), a failed
`SetModel`/`/effort`/`/mode` (no change = no write).

Implementation:
- Do the write **asynchronously** (a `tea.Cmd` from `Update` — a goroutine + a tiny result `tea.Msg`)
  so a slow disk doesn't freeze the UI, or synchronously at a defined edge if the async option
  would complicate tests — pick one, document it in the code comment, and make the failure
  behaviour test-observable through it (the model must reach one of the two states below
  deterministically in both modes; prefer synchronous in tests via an injectable
  `saveSettings func(path, model, effort, mode string) error` **field** so tests never touch the
  real `os` layer).
- Failure handling (A11): one info block `could not save settings: <err>` appended to the
  **current tab's** conversation (visible in `View()`), one line only, and nothing else changes:
  the change itself stays applied (the file just didn't persist), no retry, no overlay, no exit.
  The message is redacted like all conversation text (an error that might embed a path/secret
  passes `m.redact`).
- No other rendering change: R15 says the UI is otherwise unchanged.
- Never write a secret: `SaveSettings` gets three plain strings from the session (model id,
  effort name, mode name) — assert in the test that no key-API material can reach this path
  (no `Options`-carried config object is passed).

Tests in `internal/tui/settings_test.go` (names exact; temp `HOME`, injectable
`saveSettings`/fake failing saver; the fake-provider model helper):
- `TestModelChangeWritesSettings`: `/model <some id>` (via `m.Command`) with a stub saver that
  records calls → the stub got exactly one call with the new model id plus the current
  effort/mode; one stub call per change (a second `/model` on a different id → a second call).
- `TestEffortAndModeChangesWriteSettings`: `/effort high` and `/mode auto` each fire one call
  with the right values; the model of the call is the session's current one.
- `TestResumeValuesWriteSettings` (the A6+A11 tie-in): run the T202 restore path
  (`Options.ResumeData`) with an injectable saver → exactly one call carrying the file's
  model/effort/mode.
- `TestSettingsWriteFailureShowsOneLine` (negative): a failing stub (error text chosen to be
  redaction-safe, e.g. `disk full`) → the view contains exactly one `could not save settings:`
  line (count occurrences of the prefix in the stripped view: exactly 1) and the change applied
  (`/mode auto` still reports auto in the status; the model change still reports the new id);
  no overlay/no other block, no exit.
- `TestSettingsWriteFailureRedactsSecretInError` (negative): make the stub error text contain
  `SECRET123` and a configured redactor → the rendered line shows `[redacted]`, not the secret.
- `TestNoSettingsWriteOnNoChange` (negative): `/model <already-current id>` and `/mode` toggling
  to the already-current mode → zero stub calls (nothing was written for a no-op).
- `TestNoSettingsWriteWhenPathEmpty` (negative): `Options.SettingsPath == ""` → zero calls (the
  disabled case is genuinely disabled; relevant for existing tests that construct `Options`
  without the new field — they must keep passing unchanged).

## Verification
`scripts/verify/v3/T602.sh` exits 0. It runs these tests by name plus the whole
`./internal/tui` package, and negatives: a failing write shows exactly one
`could not save settings:` line and keeps the change applied, a no-op change writes nothing, the
disabled path (`SettingsPath` empty) writes nothing, the error line is redacted for a
`SECRET123`-carrying error, the protected paths diff (`internal/tools`, transport) stays empty,
and `make check`.
