## Brief
New file `e2e/retry_test.go` (package `e2e`; reuse the helpers of `e2e/helpers_test.go`,
`e2e/session_test.go`, `e2e/question_test.go`: temp dir, temp `HOME`, the recording fake provider
`providertest`, the program-level drive through `Model.Update`). Use the fake's scripted failure
modes (`providertest.NewWithFailures`, `Fail503`, `Fail429`, `FailReset`) and stub the retry wait
through `Session.SetRetryWait` (T605) so nothing sleeps.

Tests (names exact):
- `TestRetryTwoFailuresThenStream`: 2× 503, then a streamed answer; submit one user message; the
  turn completes (the answer is in the view, the turn is finished) and the fake recorded exactly 3
  requests with identical bodies; the stubbed waits seen were exactly 1s then 2s.
- `TestRetryStatusVisibleWhileWaiting`: with the wait stub blocked on a channel, after the first
  failure the stripped `View()` shows `retrying (2/10) in 1s`; releasing the wait clears it once
  the answer streams.
- `TestRetryNo400RetryEndToEnd` (negative): a 400 → exactly 1 recorded request, the redacted error
  line appears in the view, no `retrying` text anywhere.
- `TestRetryGivesUpAfterTenAttempts` (negative): ten scripted failures → exactly 10 recorded
  requests, an error line in the view, no further attempt (wait stubbed, never blocked).
