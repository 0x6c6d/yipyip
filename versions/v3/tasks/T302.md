# T302: Retry loop in client.go

Phase 3 · Model: opus: Consequential/A-Risk retry behaviour, only pre-first-byte, only the
host-restricted transport, exact waits — a wrong retry policy is hard to redo · Depends-on: T301 ·
Covers: R37, R12 (changed), R18 (no other host), R15 (status event surface)

## Brief
Add the retry loop to `internal/provider/client.go` **only** (no other provider file), reusing the
existing host-restricted transport untouched. Change of failure behaviour per R12/R37; the request
shape stays identical.

**Loop:** before returning any response, classify the failure:
- retryable (before the first SSE byte): dial/TLS/write timeout, connection reset (incl. "server
  closed nothing received"), HTTP 429, HTTP 5xx;
- not retryable: any other 4xx (400 bad request, 401 auth …), and any failure **after** the first SSE
  byte has arrived (a broken stream is a normal redacted `ErrorEvent`, unchanged v1 behaviour).
Retryable failures: up to **10 attempts total** (i.e. 9 retries), waits between attempts exactly
`1s, 2s, 4s, 8s, 16s, 32s, 60s, 60s, 60s` — inject the wait: a package-level `var retryWait = func(n
int) time.Duration {…}` or a field on `Client`, so tests stub it (no sleeping in tests, ever).
Identical retry request: same `context.Context` (respect cancellation — a cancelled ctx during a
wait aborts without a further attempt), same body bytes, same transport/host. Never contact any
other host: the retry uses exactly the same `http.Client` built by `transport.go`.

**Status event:** on the first retry, emit through the existing event channel a distinguishable
status event carrying the attempt number and wait, rendered by the TUI later (`retrying (n/10) in
<wait>` is the final surface in phase 6's status work — here the event text/fields must be
sufficient: `n` 2..10 and the wait duration). Keep event typing additive: do not change any
existing event type's meaning; old TUI code may ignore it.

**Tests** in `internal/provider/client_test.go` (or a new `retry_test.go`, same package; names
exact; use the fake provider's new scripted modes from T301; stub the wait — assert the recorded
waits and attempt count):
- `TestRetryNineFailuresThenSuccess`: 9 scripted resets on attempt k, stream on 10 → the client
  streams the answer; the fake recorded 10 requests, all with the same body; the recorded waits are
  exactly the nine values above in order; no wait is recorded after the success.
- `TestRetry429And5xxAreRetryable`: 10 attempts, mixing 429 and 503 in the 9 failures; success on 10.
- `TestNoRetryOn400` (negative): a 400 → exactly 1 recorded request, no retry event, the existing
  redacted error arrives.
- `TestNoRetryAfterFirstByte` (negative): the fake sends the first SSE byte then breaks the stream →
  exactly 1 recorded request, normal `ErrorEvent`; streaming errors never retry.
- `TestRetryCancellation`: cancel the context during the 2nd wait → no third attempt (≤2 recorded
  requests), no panic.
- `TestRetryNeverOtherHost` (negative): the fake's recording shows every request hit the configured
  host; assert the client's request URL host equals the fake's host for all attempts (and add a
  package-level regression guard if one is cheap — e.g. reuse the existing transport test's
  foreign-host rejection test pattern offline).
- `TestRetryEventFields`: the status events observed across a 2-failure flow have `n` = 2 and 3 and
  increasing waits (structure only, no colouring).
