# T502: Question overlay in the TUI

Phase 5 · Model: sonnet: an overlay in the style of the existing approval prompt
(`internal/tui/approval.go`), driven entirely by the T501 `QuestionRequest`; no new security
logic · Depends-on: T501 · Covers: R39 (overlay rendering, keys, result plumbing), R15 (new
modal), A2 (turn keeps running while the overlay waits)

## Brief
Render a centered overlay for a pending `agent.QuestionRequest` and feed the answer back via
`req.Respond(...)`. Files: new `internal/tui/question.go`, edits in `internal/tui/model.go`
(pending state + Update routing, mirroring how `enqueueApproval`/`approvalKey` are wired), tests
in new `internal/tui/question_test.go`.

**Pending state + notify**: when the agent notifies a `QuestionRequest` (T501's gate notify hook —
wire it the same way the approval gate's notify is wired in `New(...)`/`Options`), enqueue it
(copying the slice, like `enqueueApproval`) and route the next key to `questionKey`. Only one
question is pending at a time is not guaranteed by the spec — a queue like the approval's is
fine, render the first.

**Overlay** — `internal/tui/approval.go`'s style: centered over the dimmed frame, bold style
title, a hint line. Content top to bottom:
- the question text (redacted via `m.redact`, same as the approval summary — secrets in a
  model-authored question must not appear);
- one row per option (≤ 6, the slice is already capped by T501): single choice renders radio
  buttons `○ label` / `● label`; multiple renders checkboxes `[ ] label` / `[x] label`;
- one free-text row always at the bottom: label `type your own answer` with the active cursor
  when selected (bind it to a small single-line input; reuse the existing textarea only if its
  single-line use is trivial — a plain `[]rune` buffer + `String()` is enough);
- a hint line `↑/↓ move · Space select · Enter confirm · Esc cancel`, dim.

**Keys** (`↑`/`k` up, `↓`/`j` down, wrap at the last row = no wrap: stop at the edges like the
approval prompt):
- `↑`/`↓` move the row cursor (options + the free-text row; the free-text row is reachable by
  moving down past the last option).
- `Space`: on an option in single mode moves the `●` to that row (exactly one selected);
  on an option in multiple mode toggles `[ ]`/`[x]`; on the free-text row it does nothing (typing
  goes there, see below).
- Typing (any other printable key) while the free-text row is selected goes into the free-text
  buffer; `Backspace` deletes a rune.
- `Enter` confirms: single mode → the `●`-marked label (or, if the free-text row has typed text
  and no option is selected, the free text); multiple mode → all `[x]` labels joined with `", "`;
  if nothing is selected in either mode and the free text is non-empty, the free text; if nothing
  at all is selected, do nothing (do not send an empty result; the overlay stays).
  Confirm calls `req.Respond(<result string>)` and closes the overlay.
- `Esc` → `req.Respond(agent.Cancelled)` (`"cancelled"`, the T501 constant) and closes.
- The turn is already running (A2); the conversation/stream keeps rendering while the overlay is
  up (do not gate Update on the overlay other than for keys).

Tests in `internal/tui/question_test.go` (names exact; the fake-provider helpers with a scripted
provider that calls `question`; drive `Update` with `tea.KeyMsg`s and assert on the
ANSI-stripped `View()`; use `withColorProfile` for any colour assertion):
- `TestQuestionOverlaySingleChoiceRadio`: multiple=false, 3 options → the stripped view has
  `○ a`, `○ b`, `○ c`, exactly one `●` after `Space` on row 2, and the title/help line present.
- `TestQuestionOverlayMultipleCheckbox` (contract): multiple=true, 3 options → `[ ]` on all;
  Space on rows 1 and 3 → `[x] a`, `[x] c`; the type-your-own-answer row is present.
- `TestQuestionEnterReturnsChosenLabel` (the T501 contract end-to-end): single, select row 2,
  Enter → the recorded provider request's follow-up tool result (in the fake's recorded
  conversation) is exactly `b` (or, simpler and preferred: assert via the fake-provider's
  recorded next request that the tool result message contains `b`; the e2e T503 re-does this at
  the process level, so a `QuestionRequest.Respond`-side assertion is acceptable here if the
  recorded-history plumbing makes the request-side assertion heavy here).
- `TestQuestionEnterMultipleJoinsComma`: multiple, checkboxes on `x` and `y`, Enter → the result
  is exactly `x, y`.
- `TestQuestionFreeTextAnswer`: ↓ to the free-text row, type `yes please`, Enter → the result is
  `yes please` verbatim; the free-text row is reachable in both modes.
- `TestQuestionEscCancelled` (negative): Esc → `req.Respond("cancelled")` was called (the tool
  result is `cancelled`, asserted the same way as the Enter test); the overlay is gone and the
  next turn's rendering is unchanged by the overlay's absence.
- `TestQuestionNothingSelectedEnterStays` (negative): fresh overlay, Enter → the overlay is
  still open, no `cancelled` and no empty result sent.
- `TestQuestionRedactsSecretInPrompt` (negative): configure the redactor with a secret equal to
  `SECRET123` (the tui tests' existing redactor helper); a scripted question whose text contains
  it renders the question as `[redacted]` and the free-text row un-affected.

`./internal/tui` package, and negatives: a question whose text carries a configured secret is
