# T501: Input click-to-cursor

Phase 5 · Model: sonnet: mechanical mouse hit-testing in the TUI, no security path · Depends-on: T000 · Covers: R41

## Brief
A left click inside the input field moves the text cursor to the clicked cell; a click anywhere
else does not move it.

State before this task: `internal/tui/mouse.go` handles `tea.MouseMsg` in `Model.mouse`: the
wheel scrolls; for all other events it subtracts `tabBarRows` (1, the tab bar is the top screen
row) from `msg.Y` and runs the conversation copy-on-select (press/motion/release, `cellAt`,
`selectedText`, `m.clip`, `N characters copied` notice). `View()` (`model.go`) is, top to bottom:
the tab bar (1 row), the viewport area (`m.viewport.Height` rows), the input box (a rounded
border around `m.input.View()`, the `textarea.Model` in `m.input` with `Prompt = ""`, no line
numbers, `inputRows` = 3 text rows, width `m.width - borderCols`), then 2 status rows. So the
first input text row is at screen `y = tabBarRows + m.viewport.Height + 1` and its first text
column at screen `x = 1` (the left border).

Changes (`internal/tui/mouse.go` and a new `internal/tui/inputmouse.go`; `input.go`/`model.go`
only if needed):
- Add one helper that maps a screen position to an input position, e.g.
  `func (m Model) inputCellAt(x, y int, clamp bool) (row, col int, ok bool)`, over the input rows
  as they are rendered (soft-wrapped visual rows of the textarea, including its own vertical
  scroll when the text has more rows than `inputRows`). Positions outside the 3 text rows or the
  border give `ok == false` unless `clamp` is set (then clamped to the input text rows/columns;
  the select-to-copy task builds on `clamp`). Keep it the only place that knows the input
  geometry. The textarea has no screen-to-position API: derive the cursor's visual row from
  `LineInfo()`/`Line()` and move with `CursorUp`/`CursorDown` (visual rows) and `SetCursor`
  (column), or an equivalent approach that matches what `m.input.View()` shows.
- On a left-button press inside the input text rows: move the cursor to that cell, clamped to the
  end of that visual line (a click past the end of a line puts the cursor at its end; a click
  on an empty row below the last line puts it at the end of the text). The press must not start
  a conversation selection. Motion and release after an input press do nothing in this task
  (no copy).
- A press outside the input (conversation, tab bar, status rows, the border) leaves the input
  cursor unchanged; conversation copy-on-select (`TestCopy*`) keeps working exactly as before.

Tests (exact name) in a new `internal/tui/inputmouse_test.go`: `TestInputClick` with subtests:
an 80x24 model (`New(Options{StartDir: "/x"})` + `tea.WindowSizeMsg`), input `abc\ndefgh\nij`
(type it with runes and `alt+enter`, or `m.input.SetValue`); a click on row 1 column 2 → cursor on
line 1 column 2; a click on row 0 at column 10 → line 0 column 3 (clamped); a click on row 2
column 0 → line 2 column 0; then a click in the conversation area, one on the tab bar row and
one on a status row → cursor unchanged; no clipboard write happens for any of these clicks
(use `Options.Clipboard` with a recorder). Read the cursor with `m.input.Line()` and
`m.input.LineInfo()` (column = `LineInfo().StartColumn + LineInfo().ColumnOffset`).
