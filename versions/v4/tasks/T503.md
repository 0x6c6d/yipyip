# T503: Tab bar layout with `×` / `+` and 1-row bounds

Phase 5 · Model: sonnet: rendering and layout arithmetic in the TUI, no security path · Depends-on: T000 · Covers: R44, R43 (drawing of `×` and `+`, no `+` at 8 tabs)

## Brief
The tab bar (top screen row) gets a `×` at the end of every segment and a `+` after the last
one, and always fits in exactly one row of the window width. Clicks are a later task; this task
produces the layout including the hit zones that the click task will use.

State before this task: `internal/tui/tabbar.go` has `tabBarRows = 1`, `newSessionTitle`,
`tabCurrentStyle` (bold), `tabOtherStyle` (color 244), `(m *Model) tabTitle(i) string` (redacted
session title or `new session`) and `(m Model) tabBar() string`, which joins `"<N>:<title>"`
segments with one space and cuts the line with `ansi.Truncate` to `m.width`. `View()` puts
`m.tabBar()` as its first line. The tab limit is 8 (`errTabLimit` in `tabs.go`; find the constant
there). `internal/tui/tabbar_test.go` asserts the old format in `TestTabBarRendersSegments` and
`TestTabBarNotShownWithOneFreshTab`.

Changes (`internal/tui/tabbar.go`; adapt `internal/tui/tabbar_test.go`; new test file):
- Format: segment i is `<N>:<title> ×` (N = i+1, one space before `×`); segments are joined by
  one space; when fewer than 8 tabs are open the line ends with ` +` (one space, then `+`); at 8
  tabs no `+` is drawn. The current segment (whole `<N>:<title> ×`) is rendered with
  `tabCurrentStyle`, the others and the `+` with `tabOtherStyle`.
- Bounds (R44; the line never wraps and its display width never exceeds `m.width`):
  1. If the full line fits, use it.
  2. Otherwise truncate every title to the same budget of display cells (largest budget that
     fits, but at least 8 cells; a cut title ends with `…` inside its budget).
  3. If it still does not fit at 8 cells, collapse the segments left of the current tab to `…`
     (1 cell each, still separated by one space), leftmost first, until it fits.
  4. Still too wide: collapse segments right of the current tab to `…`, rightmost first.
  5. Still too wide: drop the `+`.
  6. Still too wide: cut the current title further (the current `<N>:` and as much title as fits
     stay visible; the `×` of the current segment stays visible if at least `<N>: ×` fits).
- Hit zones: compute the bar in one function, e.g.
  `func (m Model) tabBarLayout() (line string, zones []tabZone)`, with
  `type tabZone struct{ start, end, tab int; kind tabZoneKind }` (display columns `[start, end)`
  on screen row 0; kinds `tabZoneSwitch` for the `<N>:<title>` or collapsed `…` part,
  `tabZoneClose` for the `×` cell, `tabZonePlus` for the `+` cell, with `tab = -1` for `+`).
  `tabBar()` returns the line of `tabBarLayout()`; nothing else renders the bar.
- Adapt the old tests to the new format (and keep their names): `TestTabBarRendersSegments`
  expects `1:first question × 2:new session × +`, `\x1b[38;5;244m1:first question ×\x1b[0m` and
  `\x1b[1m2:new session ×\x1b[0m`; `TestTabBarNotShownWithOneFreshTab` expects
  `1:new session × +`. No other existing test changes.

Tests (exact names) in a new `internal/tui/tabbar_bounds_test.go` (use `newSessionModel`,
`tabTurn`, `mustAddTab`, `tabBarLine` from the existing test files): `TestTabBarBounds`: 8 tabs
whose titles are 60 runes long (each tab gets a turn with a long first message), for widths 60
and 120 and current tab 1, 4 and 8: the first view line has no line break, display width ≤ the
width, contains `<cur>:` and the current segment's `×`, the whole `View()` has the window height,
and no `+`; at width 120 all of `1:` … `8:` are visible; at width 60 at least one segment is
`…`. `TestTabBarZones`: for 3 tabs at width 160 the zones are in order, do not overlap, the
`tabZoneClose` zone of each tab covers the column of its `×` in `tabBarLine`, and the
`tabZonePlus` zone covers the `+`; with 8 tabs there is no `tabZonePlus` zone.
